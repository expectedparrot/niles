niles CRM Command Sessions

Simulated one-by-one command sessions based on the outreach workbook. The workbook is source material for realistic CRM cases, not an import target.

Setup Accounts People Notes Debrief Queue Intake Status Updates Recommendations Team & Tasks Reports Findings

Source Patterns

The current spreadsheet approximates a CRM with company rows, separate people rows, dated notes, loose next steps, and occasionally ambiguous names. These sessions show the same work as explicit niles commands.

Spreadsheet Patternniles Command ShapeStress Point
Priority 1 company with current statusniles contact add ... --trait priority=1 --tag prospectCompany-as-contact wording is usable, but not elegant.
Dated cell such as "Waiting for contract!"niles note add ... --at 2026-09-01Historical note timestamps need explicit support.
Loose "next step" proseniles task add ... --due ...The user needs a low-friction path from note to task.
Ambiguous POC namesniles contact show chatterjeeFuzzy refs must block mutating commands.
Ask others for current statusniles status-request publish ...Humanize should update the CRM only after review.
Ask what to do nextniles recommend export ... .epniles prepares jobs; ep runs them; niles imports audited results.
John / Robin ownershipniles teammate add ...Tasks need assignees, not just contact-level due dates.

Design Findings

Findings from translating the sheet habits into hand-entered CRM commands.

No ragged workbook import in v1. The sheet is a migration aid and design prompt. Keep v1 import narrow: clean CSV with an explicit mapping.
Historical note timestamps matter. To recreate dated spreadsheet updates manually, note add --at is more important than broad import support.
Company rows need language discipline. If v1 keeps only Contact, examples should consistently mark account-like records with trait.kind=account.
Debrief routing is the useful abstraction. It turns loose meeting notes into structured tasks and traits without making the user fill a full CRM form every time.
Hidden JSON improves readability. Humans scan commands first; agents and tests can expand the exact envelope when needed.
Ambiguous refs are unavoidable. Similar names and companies should produce structured candidate lists and never mutate by fuzzy guess.
Status requests are intake with a target. A humanized status-update survey needs the same quarantine and review gate as customer-facing intake.
Recommendations need an artifact boundary. The clean shape is export a .ep EDSL job bundle, run it with ep, import results into a review queue, then accept selected recommendations into tasks or notes.
Tasks replace reminders. A due-date reminder is just an open task with an optional assignee; keeping one model makes ownership and reporting simpler.
Company context belongs in local state. Recommendations and reports need stable org context and teammate aliases such as JJH/RBY without relying on prompt text scattered across jobs.
Reports are projections. Pipeline, activity, and neglect reports should be read-only views over events and the index, with export as a convenience rather than new state.
